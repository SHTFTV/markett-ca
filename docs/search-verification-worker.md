# Sequential search verification runtime

Existing GitHub Actions runs one named site per invocation every 15 minutes. Separate watchdog workflow runs at minutes 7/22/37/52. Provider schedules are best effort; configured due times are not proof of dispatch. Push bootstrap runs and schedule events must be reported separately.

Queue/checkpoints are public sanitized operational metadata in `search-worker-state` branch, `search-worker-state.json`. The branch has deployments disabled. GitHub concurrency serializes state writers; every contents update uses its expected blob SHA. A three-minute lease is saved before any provider read. A crash leaves a resumable running job; a fresh lease rejects duplicates. Completed checks become eligible for daily rechecks. Blocked checks retry after six hours after initial queue traversal. Treatments.tv is excluded from execution. No IAM campaign queue or publisher is created or reseeded.

The first runs proved no Google/Bing runtime credentials were configured. Signed-in browser sessions and GSC Wizard subscription errors do not constitute unattended API authorization. The worker reports blocked, null totals and exact owner action. No purchase is attempted. Existing-account authorization must be installed directly into GitHub Actions secrets by the owner: `SEARCH_GOOGLE_CLIENT_ID`, `SEARCH_GOOGLE_CLIENT_SECRET`, `SEARCH_GOOGLE_REFRESH_TOKEN` (read-only Search Console grant) and `SEARCH_BING_API_KEY`. A temporary `SEARCH_GOOGLE_ACCESS_TOKEN` fallback is supported but expires and is not a durable replacement. Never paste secrets in chat or commit them. Runtime credentials are never projected into public state.

Provider adapters use Google Sites GET and Sitemaps LIST and Bing GetUserSites/GetFeeds. These are reads only. DNS verification and sitemap submissions still require individually reviewed exact actions and provider access; this runtime does not silently migrate or change sites. Google processed zero-error sitemap and Bing explicit Success are counted separately from ownership; absent evidence stays null. Documentation: https://developers.google.com/webmaster-tools/v1/sitemaps and https://learn.microsoft.com/en-us/dotnet/api/microsoft.bing.webmaster.api.interfaces.iwebmasterapi.getfeeds?view=bing-webmaster-dotnet .

The watchdog runs independently of the executor, detects a heartbeat older than 45 minutes, blocked/failed/approval-required runtime and overdue publications from the live portfolio endpoint. Unknown publication monitoring is explicit. Public alerts and recoveries are persisted and deduplicated by condition. The deliberately stopped test probe is marked TEST, is detected by the watchdog, recovered by a real executor run and resolved by a subsequent watchdog. No production worker is stopped for this test.

`/api/search-worker` reads the mutable checkpoint branch rather than a deployed snapshot; the public GitHub contents API is projected with a two-minute CDN cache to stay within public rate limits. Runtime and monitor timestamps remain authoritative and stale conditions are derived at read time. The command center refreshes every 30 seconds while open and shows persistent alerts and actual run links. Codex automation `alert-on-portfolio-worker-health-changes` supplies separate local in-product health checks; its configuration alone is not proof of notification delivery. Local automation requires Codex availability and cannot guarantee alerts while the app is stopped or approvals block its chat. The GitHub watchdog continues independently.

Pending approvals in other Codex chats are not accessible to the hosted GitHub workflow. The read-only Codex health automation inspects that status; no unsupported hosted chat monitoring is claimed. This is a remaining integration limit, not a green requirement.

## November 10 onboarding executor extension

The same sequential runner contains an onboarding adapter, disabled in its deployed workflow pending exact activation approval. When explicitly enabled after that gate resolves, it supports one bounded onboarding mutation per invocation: Google Sites add, exact ownership challenge, verification-only registrar append, Google ownership check, Google sitemap PUT, Bing AddSite/VerifySite/SubmitFeed. The existing queue lease and expected-SHA checkpoint are saved before each mutation. No bulk import, deletion, routing, nameserver, mail or campaign write exists in the adapter. Previously rejected Mining Minute DNS remains an explicit approval hold. Private verification challenge data is excluded from public checkpoint state.

The new runner needs existing secure Google authorization with `webmasters` and `siteverification.verify_only`, existing Bing Webmaster API access and an authorized registrar credential for automated DNS. The earlier read-only Google grant is insufficient for setup. `SEARCH_GODADDY_AUTHORIZATION` maps an existing authorized registrar credential into the runner; no credential has been created, copied from browser cookies, granted broader scope or requested in chat. Missing credentials remain blockers. Public site evidence survives failed access attempts. A provider receipt alone creates pending-recheck, never verified ownership or successful sitemap fetch.

Recorded operating-site search jobs are added from existing public publication-source registrations for BeeWarm, Plow.news and Plow Installations, plus the previously recorded HVACR.news source-collection site. This extends search-job metadata only; it does not reseed IAM campaigns or mutate those sites. The canonical 109 inventory remains labelled separately.

A real interactive onboarding was executed for Arborists.io: Bing property added manually, exact challenge CNAME saved in its registrar zone, ownership confirmed by Bing, working public XML sitemap submitted. Bing's immediate receipt was Processing. Google already showed sitemap Success and 877 discovered pages. Console work is labelled interactive-browser, not unattended execution. Builders.ltd's exact Google TXT challenge was obtained but no DNS save/verification is claimed: isolated registrar access is signed out and the native browser is under active user control.

Automatic review rejected enabling queue-wide future onboarding mutations on November 10. The workflow explicitly sets ONBOARDING_ENABLED=false. No alternate trigger or environment path was used to activate it. Source is reviewable; manual named-site console progress remains separate.
